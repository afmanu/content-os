# Índice de operaciones de content-os

> ROOT CONTRACT: read product rules from `CORE_ROOT` and all user state/artifacts from the explicitly resolved `INSTANCE_ROOT`. References to `state/`, `docs/STATE.md`, `ideas/`, `radar/`, `research/`, `lab/`, `audits/`, `outputs/`, and `postproduction/` are relative to `INSTANCE_ROOT`. If the resolver returns `NOT_CONFIGURED`, stop with `SETUP REQUIRED` except when an explicit ONBOARD FIRST SETUP request is creating that context; never use templates as live state.


Este índice distingue lo disponible de lo planificado. Un contrato preparado no acredita una ejecución satisfactoria ni amplía permisos. RADAR e IDEA son entradas separadas: RADAR descubre oportunidades; el material proporcionado directamente por the configured human operator es un encargo editorial. **USER-PROVIDED MATERIAL IS A COMMISSION, NOT A DISCOVERY CORPUS.** Ambas entradas crean o desarrollan `CONTENT`, el núcleo editorial independiente del canal. `OUTPUT` convierte ese núcleo en una expresión concreta para un canal registrado; un CONTENT admite 0..N OUTPUTS y no existe distribución automática. Después de la decisión de the configured human operator, un CONTENT puede requerir RESEARCH, EXPERIMENT, BUILD o, con evidencia suficiente, OUTPUT directo. BUILD prepara el paquete, the configured human operator construye y BUILD incorpora y verifica la evidencia; HUMAN EXECUTION no es una operación de Codex. Para `channel: youtube`, OUTPUT enruta al motor existente y PRODUCTION confirma un `PRIMARY FORMAT` mediante [`YOUTUBE-FORMATS.md`](../channel/YOUTUBE-FORMATS.md). Las operaciones requieren órdenes separadas y ninguna recomendación encadena la siguiente. LEVEL-UP gobierna mejoras pequeñas del propio `content-os` con aprobación humana; LINK hace encontrables recursos existentes sin duplicarlos ni cambiar ownership; ambas permanecen fuera del flujo editorial. Una única orden puede cubrir varios modos internos de POSTPRODUCTION solo bajo el scope multietapa expreso de ese workflow; publicación siempre requiere autorización aparte. REVIEW no recoge métricas automáticamente y REPURPOSE crea un OUTPUT desde otro OUTPUT sin publicar.

```text
RADAR → descubrimiento → CANDIDATE ─┐
                                    ├→ decisión de the configured human operator → ruta necesaria
COMISIÓN DIRECTA → SOURCE INTENT ───┘
```

El flujo principal, con ramas opcionales según evidencia, es `IDEA / RADAR / COMMISSION → CONTENT → RESEARCH / BUILD / EXPERIMENT según necesidad → OUTPUT → CHANNEL ROUTE → REVIEW / PUBLISH cuando corresponda`. Para YouTube, `CHANNEL ROUTE` es `PRODUCTION → MANUAL RECORDING → POSTPRODUCTION → PUBLICATION-PACKAGE`; REPURPOSE crea otro OUTPUT desde uno existente. La grabación y HUMAN EXECUTION de BUILD son acciones humanas. STATUS consulta el estado declarado; LINK ajusta únicamente findability; el validador comprueba invariantes estructurales; AUDIT contrasta capabilities y evidencia sin reparar el sistema; LEVEL-UP aplica una mejora solo después de aprobación explícita.

| --- | --- | --- |

## Convenciones del registro

[`state/pieces.json`](../state/pieces.json) es la fuente canónica del **estado operativo actual**; `docs/STATE.md` conserva el historial de construcción, comprobaciones y decisiones, sin otra lista paralela vigente. El registro contiene `schema_version: 1`, la fecha real `updated_at`, el array `pieces` y, de forma opcional y backward-compatible, el array `outputs`. Ausencia de `outputs` equivale a cero outputs.

Cada entrada utiliza:

- `id`: `CONTENT-NNN` único. Para una entrada nueva se usa el entero posterior al mayor ya asignado; no se renumera ni reutiliza un ID retirado.
- `type`: `content` para altas nuevas. `youtube_video` permanece admitido únicamente como valor legacy sin migración obligatoria.
- `editorial_question` y `working_title`: texto respaldado por el expediente o `null` si no consta. Un título de trabajo no es definitivo.
- `format`: etiqueta operativa histórica o `null`. En nuevos CONTENT es `null`; el formato publicable pertenece al OUTPUT. No sustituye el `PRIMARY FORMAT` audiovisual del brief y no obliga a migrar piezas existentes.
- `origins`: referencias comprobables a rondas, candidatas e investigaciones o labs. Una candidata que origina un lab permanece en la misma entrada; compartir una investigación no obliga a fusionar piezas.
- `stage`: fase amplia del proceso, según la tabla siguiente.
- `status`: situación concreta en `snake_case`; no sustituye la fase ni implica aprobación.
- `next_action`: una sola acción o decisión siguiente; `blockers`: impedimentos documentados, sin convertir incertidumbre en hecho.
- `artifacts`: rutas relativas al repositorio de **archivos existentes**; `state_evidence`: rutas relativas existentes que respaldan el estado asignado. Las referencias de origen pueden apuntar a un directorio de lab existente o a una candidata identificada dentro de una ronda existente.
- `approvals.recording` y `approvals.publication`: booleanos independientes. `false` significa «sin aprobación explícita registrada», no rechazo; `true` exige una aprobación explícita localizable. Ni guion, revisión ni ensayo la sustituyen.

El CONTENT completo se recupera de esa entrada y sus artifacts: source/intent, subject, tesis, audiencia/problema, evidencia e investigación, Creator Advantage, claims/límites y builds o experimentos cuando existan. No se añaden esos campos a todas las piezas históricas por rutina ni se copian dentro de cada OUTPUT.

Una edición se identifica como `EDIT-NNN`. El registro puede enlazar únicamente su `postproduction/EDIT-NNN.md` seguro; paths privados, transcript crudo, manifest técnico, metadata y medios quedan fuera del repositorio. Rough cut, visual draft y final edit mantienen aprobaciones separadas por versión en ese archivo. No se añaden a todas las piezas campos vacíos ni una segunda fuente de estado. El dashboard proyecta estos datos y los OUTPUTS en modo lectura; `state/pieces.json` sigue siendo la fuente operacional.

Cada entrada de `outputs`, cuando exista, usa el contrato de [`OUTPUT.md`](OUTPUT.md): `output_id`, `content_id`, `channel`, `origin`, `source_output_id` cuando corresponda, `angle`, `format`, `promise`, `status`, `artifact` y `review_status` opcional. Los IDs `OUTPUT-NNN` son globales y no se reutilizan. `DIRECT` representa `CONTENT → OUTPUT`; `REPURPOSED` representa `OUTPUT → OUTPUT`, exige source existente del mismo CONTENT y no admite ciclos. Todo artifact registrado debe existir. Las piezas legacy sin outputs siguen siendo válidas.

| `stage` | Significado |
| --- | --- |
| `candidate` | Pregunta editorial registrada; selección o dependencias todavía pendientes. |
| `research` | Investigación en curso o pendiente de decisión sobre sus resultados. |
| `ready_to_produce` | Investigación aceptada para desarrollar una pieza; paquete editorial aún no preparado. |
| `production` | Desarrollo de brief, guion y recursos, y preparación para la grabación; no supone aprobación para grabar ni publicar. |
| `postproduction` | Existe una edición `EDIT-NNN` en preparación o revisión sobre material grabado; no supone aprobación final ni de publicación. |
| `published` | Publicación realmente realizada y documentada. |
| `reviewed` | Resultados de una publicación revisados y documentados. |
| `parked` | Pieza aplazada o archivada mediante decisión explícita de the configured human operator, con motivo registrado; una recomendación de esperar no basta. |

En `postproduction`, los estados mínimos disponibles son `awaiting_media`, `postproduction_prepared`, `rough_cut_ready_for_review`, `rough_cut_approved`, `visual_draft_ready_for_review`, `visual_draft_approved`, `final_edit_ready_for_review` y `final_edit_approved`. Se usa únicamente el que esté respaldado por el registro seguro de `EDIT-NNN`; ninguno implica `approvals.publication: true`.

Para BUILD, `ready_for_human_build` significa que el paquete manual está completo, no que el objeto exista. `evidence_partial` y `ready_for_verification` describen la evidencia recibida; solo `build_verified` acredita una verificación suficiente. HUMAN EXECUTION permanece fuera del workflow automático y no añade otro store.

Si el estado no puede determinarse, se registra la ambigüedad y una acción de aclaración. No se infieren ensayos, grabaciones, publicaciones ni autorizaciones a partir de la existencia de materiales.
